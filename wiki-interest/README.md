# wiki-interest: методологія, перевірка, розвиток

Agent Skill, що за переглядами Wikipedia відповідає на питання «чи зростає інтерес до теми,
де саме і наскільки цьому можна довіряти». Встановлення й запуск описано в
[кореневому README](../README.md).

```
SKILL.md                  інструкція для агента (≈5 КБ, розрахована на Haiku-клас моделей)
install.py                копія або архів (--zip), .venv з numpy і matplotlib, doctor
scripts/wiki_interest.py  CLI: resolve / analyze / show / report / check-answer / cache / doctor
wikitrend/                уся робота з даними: api, cache, resolve, metrics, analyze,
                          i18n (тексти uk/en), lang_check, answer_check, charts, report
references/               methodology.md (метрики й пастки), uk_style.md (глосарій)
tests/                    pytest на фейковому API (tests/fake_api.py), лише в репозиторії
evals/                    сценарії для справжнього агента + LLM-суддя, лише в репозиторії
```

## Методологія

Деталі й усі пороги — у [`references/methodology.md`](references/methodology.md) і в
константах на початку `wikitrend/metrics.py`.

- **Дані.** Wikimedia Pageviews API, лише `agent=user` (без ботів). Перегляди редиректів
  додаються до статті, тож перейменування не виглядає як обвал. Статті в різних мовах
  зіставляються через Wikidata.
- **Сплески.** День ≥ 2× від 29-денної медіани і > 5 робастних SD вище неї. Такі дні
  прибираються з трендів; частка й дати сплесків показуються окремо.
- **Тренд.** Регресія на лог-шкалі + тест Манна–Кендалла. За сильної сезонності — модель із
  місячними фіктивними змінними й сезонний тест Манна–Кендалла.
- **Нормалізація.** «На мільйон переглядів розділу» порівнює мовні розділи різного розміру.
  Відносний тренд відділяє інтерес до теми від загального падіння трафіку Вікіпедії.
- **Вердикт і довіра.** `growing` / `slow_growth` / `stable` / `slow_decline` / `declining` /
  `unclear`. Довіра (висока/середня/низька) знижується за малу аудиторію, сплески, коротку
  історію, суперечність тренду з YoY чи з відносним трендом і розбіжність між темами. Кожне
  зниження має текстове пояснення.
- **Кеш.** SQLite: повторні й розширені запити докачують лише відсутні дні. Дні, яких API ще
  не опублікував (останні 3 дні), не вважаються покритими.

## Як перевірено

1. **Тести** (`python -m pytest -q tests`, офлайн). Кожне правило статистики перевіряється на
   ряді з відомою відповіддю: ріст +40% → `growing / high`; віральний сплеск не створює
   тренду; сезонний ряд без росту → `stable`; падіння всього розділу видно через відносний
   тренд. Також: кеш, HTTP-клієнт на локальному сервері, повний CLI-сценарій, перевірка мови
   і регресійні тести на знайдені помилки (`tests/test_regressions.py`).
2. **PDF** рендериться в PNG і переглядається: одна сторінка, без накладань, кирилиця.
3. **E2E з агентом** (`evals/run_evals.py`, лише справжній API). П'ять сценаріїв (три приклади
   із завдання, сплеск, мала аудиторія) і уточнення в тій самій розмові. Автоматично
   перевіряється, що агент викликав скрипт, а не писав свій код, узяв правильні мови й
   період, створив PDF, пройшов `check-answer` і вклався в ліміт кроків. LLM-суддя
   (`--judge`) звіряє відповідь із JSON: вердикти, числа, довіра, відсутність вигаданих
   причин, застереження «інтерес ≠ попит», літературна українська.

**Що знайшли ранні прогони на Haiku 4.5 і що змінено.** Ці прогони йшли на фейковому API,
бо мережа середовища розробки блокувала Wikimedia; їхні результати з репозиторію прибрано.
- Haiku називав +8% «зростанням» при вердикті `stable` → вердикти `slow_growth`/`slow_decline`
  і готові рядки `headlines`.
- Haiku плутався, зводячи 12 серій → зведення за мовами.
- Haiku вигадував причини й пропускав застереження → `answer_checklist` у виводі
  інструмента та обов'язковий `check-answer` перед відповіддю.
- Звичайний тест тренду помилявся на сезонних темах (−17% замість +28%) → сезонне
  коригування.
- Кальки й русизми («року на року», «знаходиться в межах», «видання») → тексти генеруються
  українською в коді (`i18n.py`), глосарій `references/uk_style.md`, перевірка
  `lang_check.py`. Зауважень до мови стало приблизно вдвічі менше.

Evals на справжньому API треба запускати там, де є доступ до Wikimedia:
```bash
python evals/run_evals.py --model claude-haiku-4-5-20251001 --judge claude-sonnet-5
```

## Як розвивати далі

Цикл: новий тип запиту або помилка → сценарій у `evals/cases.yaml` → виправлення в коді або
підказці → прогін evals на дешевій моделі. Правило, яке підтвердили прогони: судження, в
якому модель помиляється, треба переносити з тексту `SKILL.md` у код і вивід інструмента.

**Методика**
1. **Автокореляція в тесті тренду.** Місячні значення автокорельовані, тож тест
   Манна–Кендалла й довірчий інтервал регресії занадто оптимістичні. Варто перейти на
   модифікований тест (Hamed–Rao) або блочний бутстреп і перевірити, як зміняться вердикти.
2. **Бектест довіри.** `--end` відмотує вікно в минуле. Варто систематично перевіряти, чи
   тримаються тренди з високою довірою наступні 6–12 місяців, і калібрувати пороги.
3. **Точки зламу** (changepoint detection): з якого моменту почався ріст і чи збігається це
   зі сплесками.
4. **Прогноз з інтервалами** (сезонна модель на кшталт ETS) для питань «скільки буде за рік».

**Складніші дослідження**
1. **Кластери тем:** підбирати пов'язані статті (категорії, «subclass of» і «part of» у
   Wikidata) і рахувати інтерес до кластера, а не до однієї статті.
2. **Зважене порівняння «тема × ринок»:** користувач задає ваги (ріст, розмір, частка,
   довіра), скрипт видає ранжовану матрицю й аналіз чутливості.
3. **Інші сигнали для валідації:** Google Trends, пошукові обсяги, попит на застосунки —
   окремі модулі з тим самим форматом серії.
4. **Тип доступу** (мобільні / десктоп) як ознака аудиторії B2C-застосунку.

**Більші обсяги даних**
1. **Wikimedia dumps замість API** для сотень статей: інкрементне завантаження в DuckDB або
   Parquet (`lang, article, day, views`) і векторні метрики.
2. **Пакетний режим** `analyze --batch topics.csv` з паралелізмом під ліміти Wikimedia і
   відновленням після збою.
3. **Спільний кеш** (Postgres або DuckDB-файл), щоб кілька агентів не качали те саме.
4. **Компактний вивід за будь-якого обсягу:** агент бачить top-N і агрегати, а повні таблиці
   пишуться у файли.
5. **Регресійні evals на реальних даних:** знімки відповідей API у фікстурах, щоб зміна
   порогів не змінювала попередні висновки непомітно.
