# wiki-interest: навичка агента для дослідження інтересу за переглядами Wikipedia

Agent Skill (формат `SKILL.md`), яка допомагає засновникам B2C-продуктів вирішити, **які теми
розвивати і якими мовами запускатися**. Навичка аналізує статистику переглядів Wikipedia, будує
графіки та робить PDF-звіт на одну сторінку. Для кожного висновку вона показує, наскільки йому
можна довіряти і чому.

```
wiki-interest/
  install.py                встановлення однією командою: копія, .venv, залежності, doctor
  SKILL.md                  інструкція для агента (коротка, розрахована на Haiku-клас моделей)
  scripts/wiki_interest.py  єдиний CLI: resolve / analyze / show / report / cache / doctor
  wikitrend/                код, що виконує всю роботу з даними
    api.py        Wikimedia Pageviews API, Wikidata, MediaWiki (редиректи); retry; User-Agent
    cache.py      SQLite-кеш: повторні й розширені запити докачують лише відсутні дні
    resolve.py    тема → Wikidata-елемент → назва статті в кожній мові
    metrics.py    сплески, тренд, сезонність, YoY, нормалізація, вердикт і довіра
    analyze.py    оркестрація, зведення за мовами, компактний JSON для агента
    i18n.py       усі тексти для людей: причини, вердикти, headlines, чекліст (uk/en)
    lang_check.py перевірка української: русизми, кальки, англійські слова посеред речення
    charts.py     PNG: абсолютні перегляди (лог.) + індекс зростання
    report.py     PDF A4 на одну сторінку
  references/     методологія, типові пастки, глосарій української (агент читає лише за потреби)
  tests/          fake_api.py (детермінований фейковий API) + pytest: 30 тестів статистики, кешу, мови та повного CLI-сценарію
  evals/          сценарії для справжнього агента + runner з LLM-суддею
```

## Встановлення
Після `git clone` достатньо однієї команди в корені репозиторію (потрібен лише Python 3.10+):
```bash
./setup.sh                        # встановити навичку для всіх проєктів: ~/.claude/skills/wiki-interest
./setup.sh claude haiku           # встановити й одразу відкрити Claude Code на Claude Haiku 4.5
./setup.sh claude haiku "Чи зростає інтерес до астрономії в українській Вікіпедії?"
```
На Windows те саме робить `setup.cmd`. Замість `haiku` можна вказати `sonnet`, `opus` або
повний ідентифікатор моделі. Claude Code відкривається в поточній теці, тож графіки й PDF
з'являться там. `setup.sh` передає всі параметри в `wiki-interest/install.py`, тому
працюють і параметри нижче (наприклад, `./setup.sh --project . claude haiku`).
Інсталятор копіює теку навички, створює в ній `.venv` із залежностями з `requirements.txt`
(системний Python не змінюється) і запускає `doctor`, щоб перевірити доступ до API. Агент
і далі викликає `python <skill_dir>/scripts/wiki_interest.py ...`: якщо у звичайному Python
пакетів немає, скрипт сам перезапускається в `.venv` (а Claude Code, запущений через
`setup.sh claude ...`, одразу отримує `.venv` першим у `PATH`). Повторний запуск оновлює код і
зберігає кеш.

Інші варіанти:
- `--link` — символічне посилання замість копії: зміни в репозиторії діють одразу (для розробки);
- `--dest DIR` — тека навичок іншого агента;
- `--deps-only` — лише `.venv` у поточній теці навички;
- `--system-python` — встановити пакети в поточний Python без `.venv`;
- `--zip wiki-interest.zip` — архів для завантаження в claude.ai (Settings → Capabilities →
  Skills). Там навичка працює в хмарній пісочниці Anthropic, тож і в мобільних застосунках;
  numpy та matplotlib там уже є, але доступ до `wikimedia.org` залежить від мережевих
  налаштувань виконання коду.

Скомпільованих файлів немає, залежності мають зафіксовані діапазони версій. Кеш
зберігається в `wiki-interest/.cache/`, а якщо тека навички недоступна для запису, то в
`~/.cache/wiki-interest`.

## Як це працює для користувача
Користувач пише: *«Порівняй зростання інтересу до інтервального голодування в польськомовній
та чеськомовній Wikipedia за останні два роки»*. Агент виконує одну команду:

```bash
python wiki-interest/scripts/wiki_interest.py analyze --topics "Intermittent fasting" --langs pl,cs --months 24
```

У відповідь він отримує компактний JSON. Основне в ньому — `headlines`, по рядку на серію:

```
pl:Intermittent fasting: інтерес СПАДАЄ, тренд -18%/рік (95% ДІ: від -20 до -17), місяців вище,
   ніж рік тому: 0 з 12, переглядів за день: 1 389, 159 на мільйон переглядів розділу; довіра до
   висновку ВИСОКА (виразна сезонність (пік — січень, у 2,1 раза більше, ніж у найслабший
   місяць); тренд скориговано з урахуванням сезонності)
cs:Intermittent fasting: інтерес СПАДАЄ, тренд -19%/рік (95% ДІ: від -20 до -18), ...
```

(приклад на тестових даних; `--ui-lang en` дає ті самі рядки англійською). Також у JSON є повні
метрики, рейтинг, шлях до графіка та `answer_checklist`, тобто нагадування агенту, що
обов'язково сказати у відповіді.
Уточнення на кшталт «додай словацьку» чи «візьми 3 роки» беруть уже скачані дані з кешу
й докачують лише те, чого бракує. `report` робить PDF з останнього аналізу. Агент пише
тільки заголовок, висновок і рекомендації, а цифри, таблицю, графік, застереження й
методологію скрипт підставляє сам, тож звіт не може розійтися з даними.

## Як навичка оцінює результати й перевіряє висновки
- **Тільки люди.** Використовується `agent=user`, тобто трафік без ботів. Перегляди
  редиректів додаються до основної статті, тому перейменування статті не виглядає як обвал.
- **Сплески.** День вважається сплеском, якщо він ≥ 2× від 29-денної медіани і більш ніж на
  5 робастних стандартних відхилень вище неї. Такі дні прибираються з трендів. Скрипт показує,
  яку частку переглядів вони дали і в які дати були.
- **Сезонність.** Якщо місячний патерн сильний, тренд рахується з місячними фіктивними
  змінними, а значущість — сезонним тестом Манна–Кендалла. Без цього тема з піком у січні,
  проаналізована з літа, виглядає як «зростання».
- **Нормалізація.** Показник «на мільйон переглядів розділу» дозволяє порівнювати мовні
  розділи різного розміру. Відносний тренд відділяє інтерес до теми від загального падіння
  трафіку Вікіпедії.
- **Вердикт і довіра.** Правила прості та задокументовані в `references/methodology.md`.
  Довіра знижується за малу аудиторію, сплески, коротку історію, суперечність між трендом і
  YoY, суперечність з відносним трендом, розбіжність між темами. Кожне зниження має пояснення.
- **Кілька статей на одну ідею.** Для кожної мови скрипт рахує зведену серію по всіх темах і
  показує, чи узгоджуються теми між собою.

## Як я перевіряв
1. **Юніт-тести статистики** (`pytest tests`, 20 тестів). Кожне правило перевіряється на ряді
   з відомою відповіддю:
   - ріст +40% дає `growing / high`;
   - віральний сплеск не створює тренду;
   - сезонний ряд без росту дає `stable`;
   - падіння всього розділу виявляється через відносний тренд;
   - нова стаття рахується лише за повні місяці;
   - кеш не робить повторних запитів.
2. **Візуальна перевірка PDF.** PDF рендериться в PNG і переглядається: одна сторінка, без
   накладань, підписи кирилицею.
3. **E2E на Haiku 4.5** через `evals/run_evals.py`. 5 сценаріїв (три приклади із завдання,
   сплеск, мала аудиторія) і уточнення в тій самій розмові. Автоматично перевіряється:
   - агент викликав скрипт, а не писав свій код;
   - правильні мови й період;
   - PDF створено;
   - кількість кроків не перевищує ліміту.
   Окремо **LLM-суддя** (сильніша модель) оцінює відповідь проти фактичного JSON: вірність
   вердиктам, правильність чисел, згадка довіри, відсутність вигаданих причин, застереження
   «інтерес ≠ попит».
   - **Що знайшли ці прогони і що змінено у відповідь:**
     - Haiku називав +8% «зростанням» при вердикті `stable`. Додано вердикти
       `slow_growth`/`slow_decline` і готові рядки `headlines`.
     - Haiku плутався, зводячи 12 серій. Додано зведення по мовах.
     - Haiku вигадував причини і пропускав застереження. Додано `answer_checklist` у вивід
       інструмента; це найефективніший спосіб керувати малою моделлю.
     - Звичайний тест тренду помилявся на сезонних темах (−17% замість +28%). Додано
       сезонне коригування.
   - **Прогін до мовних змін:** 5/6 сценаріїв за всіма перевірками. Єдиний провал: в уточненні агент
     не повторив, що дані синтетичні. Типова вартість — $0.03–0.07 і 4–6 кроків на запит.
   - Ці прогони йшли на фейковому API; їхні результати з репозиторію прибрано. Нові результати
     пишуться в `evals/results/` (у `.gitignore`).
4. **Якість української.** Відповіді Haiku містили кальки й русизми («року на року»,
   «знаходиться в межах», «видання» замість «мовний розділ», «в 2,1 рази», «впевненість»
   поруч із «довірою» у PDF). Причина: SKILL.md і весь вивід скрипта були англійською, і
   модель щоразу перекладала сама. Що змінено:
   - `headlines`, `reasons` і чекліст генеруються українською в коді (`wikitrend/i18n.py`,
     `--ui-lang uk`, для інших мов `--ui-lang en`): агент цитує готові рядки, а не перекладає;
   - глосарій «пиши / не пиши» у чеклісті й `references/uk_style.md`;
   - `wikitrend/lang_check.py` шукає русизми, кальки й англійські слова посеред речення:
     `report` повертає `language_warnings`, evals мають перевірку `uk_language`, а суддя —
     критерій `literary_language`.
   Результат на тих самих 4 україномовних сценаріях (та сама перевірка для всіх прогонів):
   до змін 16 і 9 зауважень за два прогони, після — 6 і 6. Кальки з таблиці глосарію майже
   зникли; лишаються поодинокі слова з власних проміжних повідомлень моделі. Змістові
   провали судді (застереження, вигадані причини) до і після на одному рівні (1–4 за прогін),
   тобто це розкид Haiku, а не наслідок змін.
5. **Обмеження середовища розробки.** Мережева політика контейнера, в якому писався код,
   блокувала `wikimedia.org` і `wikidata.org`. Тому E2E-прогони вище йшли на фейковому API.
   Тепер фейковий API є лише в тестах (`tests/fake_api.py`), а evals працюють тільки зі
   справжнім API. Команди для перевірки на справжніх даних:
   ```bash
   python wiki-interest/scripts/wiki_interest.py doctor
   python wiki-interest/evals/run_evals.py --model claude-haiku-4-5-20251001 --judge claude-sonnet-5
   ```

## Як розвивати далі (ітеративно)
Цикл розвитку: новий тип запиту або помилка → сценарій у `evals/cases.yaml` → виправлення
в коді або підказці → прогін evals на дешевій моделі. Правило, яке підтвердили прогони:
будь-яке судження, в якому модель помиляється, треба переносити з тексту SKILL.md у код і
вивід інструмента.

**Складніші дослідження**
1. **Кластери тем.** Автоматично підбирати пов'язані статті (категорії Вікіпедії, властивості
   Wikidata «subclass of» і «part of», вихідні посилання) і рахувати інтерес до всього кластера,
   а не до однієї статті.
2. **Порівняння «тема × ринок» за зваженим критерієм.** Користувач задає ваги: ріст, розмір,
   частка, довіра. Скрипт видає ранжовану матрицю і пояснює, які припущення найбільше
   змінюють порядок (аналіз чутливості).
3. **Бектест довіри.** `--end` вже дозволяє відмотати вікно в минуле. Далі варто
   систематично перевіряти, чи тримаються тренди з високою довірою наступні 6–12 місяців, і
   калібрувати пороги на цьому.
4. **Точки зламу.** Шукати момент, з якого почався ріст (changepoint detection), і прив'язувати
   його до дат і сплесків.
5. **Прогноз з інтервалами** (сезонна модель на кшталт ETS) для запитань «скільки буде за рік».
6. **Інші сигнали для валідації.** Google Trends, попит на застосунки, пошукові обсяги. Кожне
   джерело — окремий модуль з тим самим форматом серії, щоб метрики й звіт не змінювались.
7. **Розбивка за типом доступу** (мобільні / десктоп) як ознака аудиторії: мобільний трафік —
   це ближче до B2C-застосунку.

**Більші обсяги даних**
1. **Wikimedia dumps замість API.** Для сотень статей і всіх мов є погодинні дампи
   `pageviews`. Їх варто завантажувати інкрементно в DuckDB або Parquet (одна колонкова
   таблиця `lang, article, day, views`) і рахувати метрики векторно.
2. **Пакетний режим:** `analyze --batch topics.csv` з паралелізмом під ліміти Wikimedia
   (≈ 100 запитів/с, User-Agent обов'язковий) та відновленням після збою.
3. **Кеш як спільний сервіс:** SQLite → Postgres або DuckDB-файл у спільному сховищі, щоб
   кілька агентів чи користувачів не качали те саме.
4. **Компактний вивід для агента за будь-якого обсягу.** Агент бачить лише top-N рядків і
   агрегати, а повні таблиці пишуться у файли. Контекст моделі не росте разом із даними.
5. **Регресійні evals на реальних даних:** зафіксувати знімки відповідей API у фікстури і
   періодично порівнювати вердикти, щоб зміна порогів не ламала попередні висновки непомітно.
